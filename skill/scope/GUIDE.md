# 기능 정의 (scope)

목표는 사용자가 몇 분 안에 "이 기능이 무엇을 어디까지 하는지"를 파악하고, 원하지 않는 부분을 걸러낼 수 있게 하는 것이다. 사용자는 긴 글을 읽지 않는다. 첫 화면의 노드 몇 개를 보고, 궁금하거나 무거워 보이는 노드만 눌러 들어간다. 그래서 문서는 위에서 아래로 갈수록 자세해지는 트리이고, 각 노드는 한두 줄로 읽혀야 한다.

## 기능만 쓴다

이 단계에서는 동작만 정한다. 코드 구조는 다음 단계의 일이다. 기능이 깎일 수 있는데 설계까지 해 두면 그 시간이 버려지고, 설계가 섞인 문서는 사용자가 범위를 판단하기 어렵다.

어떤 문장을 노드에 써도 되는지는 이렇게 판별한다.

> 코드를 전혀 다른 구조로 짜도 이 문장이 그대로 참인가?

- "헤더는 앞 64바이트만 읽고 판별한다": 어떻게 짜든 참이다. 쓴다.
- "형식이 맞지 않으면 400으로 거절한다": 참이다. 쓴다.
- "검증 클래스가 헤더를 확인한다", "검증 로직을 미들웨어로 분리한다": 구조가 바뀌면 거짓이 된다. 쓰지 않는다.

쓸 수 있는 것은 동작, 조건, 결과, 한도 값, 닿는 외부 시스템이다. 클래스·함수·파일 이름, 라이브러리, 자료 구조, 코드 배치는 쓰지 않는다. `check`는 코드 식별자처럼 보이는 표현에 경고를 낸다. 외부 시스템이나 제품 이름 때문에 난 경고라면 그 이름을 `touches`에 넣으면 사라진다.

## 문서 형식

```json
{
  "unfold": 1,
  "stage": "scope",
  "feature": "리소스 업로드",
  "request": "FE가 올린 리소스를 검증하고 S3에 올린다",
  "status": "draft",
  "doneWhen": [],
  "excluded": [],
  "nodes": [
    { "id": "1", "title": "업로드 수신", "summary": "FE가 보낸 요청에서 파일을 받는다.", "origin": "requested", "leaf": true },
    { "id": "2", "title": "리소스 검증", "summary": "올라온 파일이 유효한지 확인한다.", "origin": "requested" },
    { "id": "2.1", "title": "헤더 프레임 검증", "summary": "앞부분의 헤더 프레임이 허용된 형식인지 본다.", "origin": "requested" },
    { "id": "2.2", "title": "악성코드 스캔", "summary": "전체 바이너리를 외부 스캐너에 보낸다.", "origin": "added", "touches": ["스캐너 API"], "leaf": true }
  ],
  "edges": [
    { "from": "1", "to": "2" },
    { "from": "2.1", "to": "2.2" }
  ]
}
```

- `request`: 사용자가 쓴 요청 문장을 그대로 옮긴다. 요약하거나 다듬지 않는다. 나중에 범위를 넘었는지 판단하는 기준이 된다.
- `nodes[].id`: `2`, `2.1`, `2.1.3`처럼 쓴다. 점 앞부분이 부모의 ID다. 사용자가 채팅에서 이 번호로 노드를 가리키므로, 한 번 화면에 나온 ID는 바꾸지 않고 지운 ID를 다른 노드에 다시 쓰지 않는다.
- `title`: 노드 상자에 들어가는 짧은 이름. 열 글자 안팎.
- `summary`: 이 동작이 무엇을 하는지 한두 문장. 값을 정했다면 그 값을 적는다.
- `touches`: 이 동작이 닿는 외부 시스템(저장소, 외부 API, 큐, 메일 등).
- `leaf`: 더 내려가도 사용자가 새로 정할 것이 없으면 `true`. 하위 노드를 아직 쓰지 않았을 뿐이면 넣지 않는다.
- `terminal`: 이 노드에 닿으면 기능의 흐름이 끝나면 `true`(예: 에러 응답).

### 출처

`origin`은 사용자가 가장 먼저 보는 정보다. 요청보다 커진 부분이 어디인지 색으로 드러나기 때문이다. 정직하게 가른다.

- `requested`: 사용자가 요청했거나, 요청한 동작이 성립하려면 반드시 있어야 하는 것.
- `assumption`: 요청 범위 안이지만 구체적인 값이나 방식을 AI가 정한 것. 사용자가 판단할 것은 "맞는가"이다. 예: 읽는 바이트 수, 응답 코드, 한 번에 올리는 방식.
- `added`: 요청에 없는데 AI가 넣으려는 동작. 사용자가 판단할 것은 "넣을까 뺄까"이다. 예: 재시도, 악성코드 스캔, 중복 검사, 알림 발송.

보안 강화, 방어적 처리, 재시도, 캐싱, 로깅, 알림처럼 있으면 좋아 보이는 것은 요청에 없었다면 `added`다. 떠오른 것을 숨기거나 `requested`에 섞지 않는다. `added`로 드러내면 사용자가 고를 수 있다.

### 선

- 선은 같은 단계의 노드끼리만 잇는다. `2.1`에서 `3`으로 가는 선은 쓸 수 없다. 그런 흐름은 부모 단계의 `2 → 3`이 이미 말하고 있다.
- `when`: 조건이 있을 때만 타는 선이면 조건을 짧게 적는다("불일치 시", "카드").
- `kind`: 앞 노드로 돌아가는 선은 `"loop"`, 한 노드에서 여러 노드가 동시에 시작되면 그 선들에 `"parallel"`을 붙인다. 보통의 순서는 생략한다.
- 자기 자신으로 가는 선은 쓸 수 없다. 반복은 노드를 둘로 나눠 뒤 노드에서 앞 노드로 돌아가는 선으로 그린다.
- 한 단계의 노드는 3~7개로 묶는다. 그보다 많으면 묶어서 한 단계 더 깊게 만든다.

## 진행 순서

### 1. 살펴보기

요청과 직접 닿는 코드만 가볍게 읽는다. 지금 이미 되는 동작이 무엇인지, 어떤 외부 시스템이 있는지 알기 위해서다. 이 단계에서 구조를 구상하지 않는다.

요청이 서로 다른 기능으로 읽힐 만큼 모호하면 그래프를 그리기 전에 한 번 묻는다. 깊이에 관한 모호함은 묻지 않고 `assumption`이나 `added`로 그래프에 드러낸다. 사용자가 그림을 보고 고르는 편이 빠르다.

### 2. 전체를 쓰고 보여주기

문서를 끝까지 쓴 다음에 보여준다. 3단계 깊이까지 쓰거나, 그 전에 모든 노드가 `leaf`가 되면 멈춘다. 더 깊은 곳은 사용자가 요청할 때 쓴다.

안쪽을 쓰다 보면 처음에는 보이지 않던 `added`와 `assumption`이 나온다. 그것이 이 단계의 목적이다. 구현할 때 내리게 될 결정을 지금 노드로 꺼내 놓는다.

다 썼으면 `check`로 오류와 경고를 고치고, `done`을 실행해 첫 리비전(r1)을 만든 뒤 `view`로 띄운다.

### 3. 짧게 알리기

사용자에게 주소와 함께 짧게 알린다. 그래프가 설명이므로 내용을 글로 되풀이하지 않는다. 알릴 것은 셋이다.

- AI가 추가한 것이 몇 개이고 어느 노드에 있는지(ID)
- 가정이 몇 개이고 그중 꼭 확인받고 싶은 것
- 고칠 때는 노드 번호로 말하면 된다는 것

### 4. 채팅으로 고치기

사용자는 화면에서 펼쳐 보기만 하고, 수정은 채팅에서 노드 번호로 말한다. 한 번의 요청에 담긴 수정을 모두 작업본에 반영한 다음 `done`을 한 번 실행한다. 그러면 화면이 새 리비전으로 바뀌고 달라진 노드에 표시가 붙어, 사용자가 전체를 다시 훑지 않아도 된다. 수정을 일부만 하고 `done`을 실행하지 않는다.

- "2.3 빼줘": 노드와 그 하위, 연결된 선을 지우고 `excluded`에 제목과 이유를 적는다. 이 목록은 구현 때 같은 것이 다시 들어오는 일을 막는다.
- "2.1 더 자세히": 그 노드의 하위 노드를 쓴다. `leaf`였다면 지운다.
- "3 더 간단하게": 더 단순한 동작으로 바꾼다. 무엇을 포기하는지 한 줄로 알린다.
- 가정을 고쳐 주면: 값을 바꾸고 `origin`을 `requested`로 바꾼다. 이제 사용자가 정한 값이다.
- `added`를 넣겠다고 하면: `origin`을 `requested`로 바꾼다.
- "아까 걸로 되돌려줘", "r2로 돌아가": `revert <파일> <번호>`를 실행한다. 리비전 번호는 화면 제목 옆에 나온다.

`done`이 끝나면 몇 번 리비전이 됐는지와 무엇을 바꿨는지 한두 줄로 알린다.

### 5. 확정

사용자가 확정하겠다고 말했을 때만 확정한다. 스스로 판단해 확정하지 않는다.

1. `doneWhen`이 비어 있으면 기능이 됐는지 확인할 수 있는 문장을 한두 줄 써서 사용자에게 보여준다.
2. `confirm`을 실행한다. 화면에 반영되지 않은 수정이 있으면 거부되므로, 그때는 `done`을 먼저 실행하고 사용자에게 다시 확인받는다.
3. 종료 코드가 2이면 사용자가 화면에서 보지 않은 `added` 노드가 있다는 뜻이다. 출력된 목록을 사용자에게 그대로 보여주고 넣을지 뺄지 묻는다. 답을 반영한 뒤 `confirm --force`를 실행한다. 사용자의 답 없이 `--force`를 쓰지 않는다.

확정되면 이전 리비전은 지워지고 확정본만 남는다. 파일 위치를 알리고 끝낸다. 이 문서가 설계와 구현의 기준이 된다.
